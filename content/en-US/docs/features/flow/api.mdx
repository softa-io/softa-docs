## API Overview

<Lead>

A business module submits, withdraws and cancels records, and previews a record not saved yet, in-process through `FlowClient`, and everything else goes over REST; both resolve identity from the server-side context, and a refused request answers in the framework's envelope with its reason.

</Lead>

| Group | Base path | Purpose |
|---|---|---|
| [Design APIs](#design-apis-flow-editor) | `/flow/designs` | The graphical editor: creating, saving, validating, publishing and test-running a draft |
| [Bundle APIs](#bundle-apis-published-revisions) | `/flow/bundles` | The history and activation of published revisions |
| [Node Descriptor APIs](#node-descriptor-apis) | `/flow/nodeDescriptors` | The node descriptors of the editor palette |
| [Instance APIs](#instance-apis) | `/flow/instances` | Launch, reads and approval actions on runtime instances; [a record's approval](#a-records-approval), [the record an approval runs on](#the-record-an-approval-runs-on), [instance search](#instance-search) |
| [Automation APIs](#automation-apis) | `/flow/automation` | Trigger firing |
| [Event Logs](#event-logs) | `/FlowEvent/searchPage`, … | The trigger event log, read through the generic model API |
| [Approval Tasks](#approval-tasks) | `/flow/approvalTasks` | The current user's task boxes and top-bar counts |
| [Approval Records](#approval-records) | `/flow/approvalRecords` | Approval history by runtime instance |
| [Delegation](#delegation) | `/flow/delegations` | Delegation rules |
| [Directory](#directory) | `/flow/directory` | What the people and department pickers list |
| [Monitor](#monitor) | `/flow/monitor` | The administrators' console |

**In-process: `FlowClient`.** Host applications embedding the engine in-process should integrate through `FlowClient` (`io.softa.starter.flow.api`, one class the auto-configuration registers — nothing to implement or replace) rather than looping back over REST. The port covers what a business module does — a record's approval: `submitRecord`, `previewValues`, `withdrawRecord`, `cancelRecord`.

Approvers act, people read their tasks, a record's approval and a saved record's submission preview are read, and an Automation flow with an `Api` trigger is started (`POST /flow/instances/start`), through REST. `FlowAutoConfiguration` registers the default `InProcessFlowClient` only when the application defines no `FlowClient` bean of its own. Putting a business model through approval is described in [Integration](./integration).

**Identity is always resolved server-side.** `actorId` / `initiatorId` / `tenantId` are **never** sent by clients: every action request stamps them server-side from the login context (`@JsonProperty(READ_ONLY)`), and all query endpoints resolve the current actor from the context. The in-process `FlowClient` resolves actor / submitter / tenant identity the same way — never passed as call parameters — and calls the same services as these endpoints.

**A refused request** answers in the framework's envelope (HTTP 200, the code in the body) with its reason as the message:

| Case | Code |
|---|---|
| An action the engine refuses (`FlowActionValidationException`) | `400` |
| A caller not allowed (`FlowAuthorizationException`) | `403` |
| A flow that does not compile | `400`, with all its diagnostics — only an `Error` refuses, a `Warning` is advice |

Any other error still reaches softa-web's `Throwable` catch-all — logged, answered `500`, its message kept out of the response.

<Dev title="Why FlowExceptionHandler is ordered first">

`FlowExceptionHandler` is ordered first (`Ordered.HIGHEST_PRECEDENCE`): Spring takes the first advice that handles an exception at all, and softa-web's `Throwable` catch-all would otherwise answer these as a bare `500`.

</Dev>

| `GET` | `/flow/designs?keyword=&scenario=&subflowTargets=&pageNumber=&pageSize=` | Paged draft list (canvas excluded); `subflowTargets=true` keeps the flows a Subflow node can call — the enabled Automation flows whose effective revision declares a Subflow trigger |

| `POST` | `/flow/designs/{id}/preview` | An approval flow's test run: what submitting a request with these field values as this user would do under the saved draft — whether its submit condition takes it, the route and each step's approvers — worked out without running anything. See [Testing a draft](./approval#testing-a-draft) |

| Method | Path | Description |
|---|---|---|
| `POST` | `/flow/instances/withdraw` | Withdraw an Approval instance: its submitter, while it waits on its approvers and the flow's `withdrawPolicy` permits it (`WithdrawPolicyGuard`). |---|---|---|

| `GET` | `/flow/instances/preview?modelName=&rowId=` | A preview of a submission only: what submitting the record would do now, without submitting it — its document's approval flow and its approval steps, each with the approvers who would be asked or why it passes on its own; a refusal, a document with no enabled approval flow or with several are reported, a route decided only once the approval runs is reported as undecided. While the record's approval is in progress, only <Status>InProgress</Status> and that submission's `instanceId`, with no steps: its steps are the record's approval's (`.../by-record`). - An action's `comment` is at most 256 characters, as a batch action's comment and an administrator's reason are; a longer one is refused (`400`) before anything runs.
- An action on a step that no longer waits — handled by someone else, or on another page, since the caller's was loaded — is refused (`400`, "This step no longer waits for approval…") rather than failed as an error, so the page refreshes and shows where the approval stands.

#### Who may view an instance

- **By default, its participants** — its submitter and the people it gives or gave a task to: approvers pending or done, CC recipients, transfer and delegation targets, and the approvers a step closed without them (the pending approvers a termination cleared, the other approvers of a step someone else's vote carried). The same participants comment on an instance while it runs and read its record past their own row permissions. Reading the record through the instance follows narrower rules: see [The record an approval runs on](#the-record-an-approval-runs-on).
- **An administrator's actions make nobody a participant**: urging or terminating an instance, or reassigning one of its tasks (recorded as the approver's `TRANSFER` with the administrator as `operatorId`), gives them no task.
- **Everyone else**, administrators included, goes through the standard role and data-scope configuration — they may read the `FlowInstance` row with their own permissions, or, for a record's approval, read the record itself.
- **A record's approval admits as a whole**: a submission is part of its record's approval, and whoever sees the record's approval views each submission of it — besides the people above, those who took part in another submission of the record, and those whose roles read the `FlowInstance` row of another (see [A record's approval](#a-records-approval)). Comments stay with this submission's participants. An automation run belongs to no record's approval, and its rule is unchanged.
- **The defaults need no grant on the flow models**, which no business role holds.
- **The current user's own lists** — inbox counts and the task search (`/flow/approvalTasks`), their delegations, and `POST /flow/instances/search` — carry `@SkipPermissionCheck`: pinned to the caller, row scope could only empty them; the filters a client adds to them are ANDed onto the pin, never in its place (see [Filtering and sorting a list](#filtering-and-sorting-a-list)).
- **The per-instance reads** (`.../instance/{instanceId}`, the instance detail endpoints) are not waived, because the guard judges everyone but the submitter and the task holders by their own permissions.

<Dev title="How participants are found, and the engine's own reads and writes">

- The instance's state and approval history name most participants (`FlowParticipants`); the rest are named only by their task, which stays when it closes, so the access guard asks the instance's `FlowApprovalTask` rows — CC tasks included, whatever their status — when the state and history name nobody, in one query however many instances it asks about (`FlowInstanceAccessGuard.isParticipant`).
- An instance endpoint (`requireInstanceViewer`) makes the instance's own checks first — a participant, a reader of the instance row, a reader of the record; only when none passes and the instance is a record's approval does it read the record's other submissions, to see whether the caller took part in one or their roles read one.
- The engine's own bookkeeping — loading and saving instances, the approval ledger, the task projection, delegation and finding CC recipients — runs past the caller's data permissions: who may act is the action handlers' call, who may see the access guard's.

</Dev>

### A record's approval

A record has one approval, holding every submission of it: each submission starts an approval instance, and the earlier ones are marked `superseded` (see [A record's approval and its steps](./approval#a-records-approval-and-its-steps)). `GET /flow/instances/by-record` returns the whole of it (`FlowRecordApprovalsView`); a record never submitted has no submission, and `instances` is empty.

- **Who sees it**: whoever can read the record with their own permissions; whoever took part in any of its submissions (participants as [Who may view an instance](#who-may-view-an-instance) names them); whoever's roles read the `FlowInstance` row of any of them, such as the monitor's administrators (a department scope judges each submission by the department it recorded, see [Monitor](#monitor)). Everyone else is refused (`403`).
- **They see it whole**: every submission, each with its steps, whichever one the caller took part in, however far the approval has gone and whether or not it has ended. The same people open each submission: its detail, `/summary`, `/design`, `/overlay`, `/trace`, `/nodes/{nodeId}/formPermissions`, `GET .../urge`, `GET .../withdraw`, and its tasks (`/flow/approvalTasks/instance/{instanceId}`) and approval records (`/flow/approvalRecords/instance/{instanceId}`). Whether they may urge or withdraw stays with each action's own rule.
- **The record's content has rules of its own**: fewer people read the record through an approval — its participants, and whoever can read the record; someone who sees the record's approval by their roles alone sees its steps, not the record (see [The record an approval runs on](#the-record-an-approval-runs-on)).

Each submission (`instances[]`, newest first):

| Field | Holds |
|---|---|
| `instanceId`, `flowId`, `flowName`, `status` | The submission's approval instance, its flow and the instance's status |
| `superseded` | A later submission of the record replaced it, or the record was cancelled |
| `initiator`, `startedAt` | Who submitted it, and when |
| `steps` | Its approval steps, in the order the approval reached them; below |
| `undecided` | While in progress: the nodes past which the route depends on data only known once the approval runs; the steps ahead stop there |
| `expectedFailure` | While in progress: the node the route ahead would fail at, and why; the steps ahead end there |
| `failure` | When it failed: the node it stopped at (`nodeId`, `nodeLabel`) and why (`message`); `retryable` says whether it failed in the steps after an approval — the approval stands and an administrator can run them again — or else its submitter takes the record back |
| `ended` | How it ended: the `action` that ended it (`Reject`, `Return`, `Withdraw`, `Terminate`; none when it completed), `actor`, `operator`, `comment`, `time`; empty while in progress or after it failed |
| `events` | Actions on the submission as a whole rather than on one step, such as an administrator running the steps after an approval again (`Retry`) |

A step (`steps[]`) has its `nodeId`, `nodeLabel` and `state` — `Done` (the approval passed it), `Current` (the approval waits on it; every step parallel branches wait on at once is) or `Upcoming` (not reached yet, only on the submission in progress) — and:

- `approvalMode` and `requiredApprovals`: the approval mode and how many approvals pass the step (the automatic ones counted; none when nobody is asked); `enteredAt`, `finishedAt`: when the approval reached and passed it;
- `approvers`: one row per approver — `actor`, `result`, `time`, `comment`; `target`, whom they transferred or delegated the step to (who has a row of their own), `operator`, the administrator who acted in their place (a reassignment), and for an automatic approval its reason (`autoApprovalReason`: `Submitter` or `EarlierApproval`);
- `outcome`: for a step not reached yet, what it is expected to do, with the values of the [preview](./approval#previewing-a-records-approval)'s `outcome`; `NoApproverApproved` for a step passed with nobody to ask; none otherwise;
- `assignedRoles`: the names of the roles a step that found nobody went to;
- `events`: the other actions on the step, in the order they happened — a copy `Cc` (`target` its recipient, `read` whether they read it), an `Urge`, a `Comment`, and `AddSign` in history recorded before it was removed; each with `actor`, `target`, `operator`, `comment` and `time`.

An approver's `result`:

| `result` | Means |
|---|---|
| `Approved`, `Rejected`, `Returned` | Approved, rejected, returned |
| `Transferred`, `Delegated` | Handed the step to `target`, who has a row of their own |
| `AutoApproved` | Counted as having approved: the submitter (under the flow's `selfApproval`), or someone who approved an earlier step (under approver dedup) |
| `Pending` | Asked, and has not acted yet |
| `NotNeeded` | No longer asked: others approved enough, or the approval was withdrawn or ended |
| `Expected` | A step not reached yet is expected to ask them, as the route stands now |

<Dev title="How a record's approval is put together">

- The submissions and their approval histories are read past the caller's permissions to decide whether the caller sees the record's approval (`FlowInstanceAccessGuard.authorizeRecordApprovals`); only then are the submissions' tasks read, in one query, the steps composed (`FlowApprovalStepsComposer`) and the users named.
- A step passed or waited on comes from its tasks (one per approver; a task closed Canceled or Withdrawn reads `NotNeeded`) and from the instance's waiting approvals (an approver with no task yet reads `Pending`); copies, urges and comments come from the approval ledger, each on the step of its node; a withdrawal or termination is the `ended`, a retry an `events` entry, and reads are not listed.
- The steps ahead are worked out by `ApprovalPathPreviewer.previewRemaining`, from the instance's own variables and approvals, never the record, for the submission in progress only, once per request at most; when that fails or the revision is not at hand, no step ahead is listed.

</Dev>

### The record an approval runs on

The approval page (`/home/approvals/{instanceId}`, the link of every approval email) is opened by approvers who may hold neither the menu of the record's model nor any permission on the flow models, so it reads everything through the instance: `GET /flow/instances/{instanceId}` and `.../summary` for the instance, `.../design` for its diagram, `.../record` for the record. Only a record's approval lends its record (`FlowInstanceAccessGuard.requireRecordAccess`):

- **Its participants — its submitter and the people it gives or gave a task to** read it past their own row permissions. They see every field, dynamic ones included, but the sensitive ones they may see on no row (`PermissionService.getHiddenSensitiveFields`); the field permissions (`formPermissions`) of the waiting steps they approve are laid over that — what a step lists as `Readonly` / `Editable` / `Required` shows, sensitive or not, what it marks `Hidden` does not, and with several steps a field any of them shows is shown. The submitter sees the default; anyone else with no waiting step — a CC recipient, an earlier approver, an approver a termination cleared — also misses what any approval step hides.
- **A one-to-many's rows follow the same rule on their own model**: each row loses the sensitive fields of its model the caller may see on no row, unless a waiting step of the caller lists the one-to-many itself as `Readonly`, `Editable` or `Required` — that grants its rows whole. A step marking the one-to-many `Hidden` leaves it out. The submitter and everyone else get the rows without the fields their own roles withhold. So a step that shows a salary adjustment's amounts to approvers who hold no salary set lists its lines: `"formPermissions": {"salaryAdjustmentDetailIds": "Readonly"}`; without it, they see the lines without them.
- **Anyone else who can read the record with their own permissions** — an administrator following a link — gets the model's ordinary permission-checked read of the same fields: their row scope, field blocks and masking, on the rows of each one-to-many too. Reading the `FlowInstance` row is not enough; everyone else is refused (`403`).

**Reading by the record.** A page keyed by the record, which shows the record's approval, cannot read the record through one of its submissions: `GET /flow/instances/by-record/record?modelName=&rowId=` returns the same `{ record, fields }` whichever submission is current:

- **The newest submission the caller took part in** — as its submitter or a person it gives or gave a task to, a terminated approval's cleared approver by their task — lends the record as `.../record` of that instance would: an approver it waits on sees the record as their step shows it; someone who took part only in an earlier submission sees what that approval shows a participant with no waiting step — the default, without what an approval step of its revision hides. The record's approval (`.../by-record`) also admits whoever's roles read one of its instances; one who cannot read the record is refused here all the same.
- **Anyone else who can read the record with their own permissions** gets the model's ordinary read, with empty `fields` — the only way a record never submitted, a draft its owner opens, is read here.
- **Everyone else** is refused (`403`). A model that does not exist is `404`, and so is a record deleted under someone who took part in its approvals; to anyone else a missing record is refused like one they cannot read, so the endpoint never tells them whether it exists. A record deleted softly — the row kept, flagged — is deleted here too: `404` to whoever is let in.

<Dev title="How the approval that lends the record is found">

`FlowInstanceAccessGuard.requireRecordAccess(modelName, rowId, requesterId)` walks the record's approvals newest first, read past the caller's permissions; the first the caller took part in lends the record. A terminated approval's cleared approver counts by their task, and those tasks are asked in one query: the tasks of all the approvals newer than the first one whose state and history name the caller.

</Dev>

**The response** is `{ record, fields }` (`FlowInstanceRecordView`):

| Field | Holds |
|---|---|
| `record` | Read as the model read API returns a record: relations and options as references, each one-to-many with its rows, a field with a `maskingType` masked |
| `fields` | By model name — the record's model, and the model of a one-to-many's rows — the definitions of the fields `record` shows that the caller's own metadata leaves out: the sensitive fields a step grants, which `GET /metadata/getMetaModel` withholds from them. Each is a `MetaFieldDTO`, as the metadata API serves a field, for the client to merge into the models it loaded. It is empty for a reader of the record and whenever nothing withheld is shown; an application without metadata-starter serves no metadata to merge them into, and gets none |

```json

    "id": "7",
    "code": "SA-0007",
```

### Instance search

`POST /flow/instances/search` (the caller's own approvals) and `POST /flow/monitor/instances/search` (across submitters, see [Monitor](#monitor)) take the same `FlowInstanceSearchRequest` and return the same rows, newest first, paged by `pageNumber` (default 1) and `pageSize` (default 50). The caller's own search is always pinned to the record approvals they submitted; the rest combine with AND on top, narrowing it, never widening it:

| Filter | Matches |
|---|---|
| `awaitingRevision` | Approvals returned to their submitter that neither a later submission of the record replaced nor the record's cancellation closed (`superseded` unset) — records still waiting to be edited and submitted again |
| `filters` / `orders` | Conditions and a sort on the stored fields of `FlowInstance`, as a metadata-driven table sends them — by flow, status, submitter, employee, department, effective date, record number or start time, all go here; `orders` replaces newest first. See [Filtering and sorting a list](#filtering-and-sorting-a-list) |

A row (`FlowInstanceSummaryView`) leaves out the heavy state columns and the trace — fetch the instance or its overlay for those. It carries:

- the flow, title, submitter, status and the steps the instance waits on now (`currentSteps`, each with the approvers still to act), every user named;
- for a record's approval, what its submission recorded (see [Approving Business Records](./integration#approving-business-records)): `subject`, `subjectDept`, `effectiveDate`, `recordCode`, `summary`, and `awaitingRevision`;
- `withdrawable` and `urge`: on the caller's own approvals that wait on their approvers, whether they may withdraw or urge them now; on their own records' approvals that failed, `withdrawable` whether they may take the record back; on the monitor search, `urge` says whether the caller may urge as an administrator — the flow's `urgeIntervalHours` decides, whatever its `urgeEnabled` says;
- `recordDeleted`, marking an approval whose record is gone — a draft deleted after a return or a withdrawal, softly too (the row kept, flagged) — and `recordCancelled`, one whose record was cancelled after it ended;
- `effectStatus`: where an approved record's change stands, for a model whose approval takes effect later (`ModelApprovalHandler.effectStatuses`).

### Filtering and sorting a list

The approval center's lists — the task boxes of `POST /flow/approvalTasks/search` and both instance searches — take, besides what each names itself, `filters` and `orders` in the grammar `Filters` and `Orders` parse, as a metadata-driven table over `FlowApprovalTask` or `FlowInstance` sends them: `[["instanceTitle", "CONTAINS", "taxi"], "OR", ["recordCode", "CONTAINS", "taxi"]]`, nested at will, and `[["submittedTime", "DESC"]]`. The rows still come from these endpoints, not the generic `/{model}/searchPage`: they pin the rows to the caller and add the names the models do not hold (`FlowUserNames`, `OrganizationService`).

- **ANDed on, never in place.** The filters narrow what the list returns anyway — the caller's pin (their own tasks, their own record approvals), the box, the typed filters, and on the monitor search the caller's data scope — as a subtree of their own, so an `OR` in them cannot reach past it: a filter naming another actor finds nothing.
- **Stored fields only.** They may name only fields the model stores. A dynamic field (`flowName`, `scenario`), a path into another model (`flowId.flowName`), a name the model does not have, or such a field compared against (`{{ @field }}`) is refused (`400`) naming the field, before anything is read (`CallerConditions`). A filter on `searchName` — the toolbar search — stands for the model's `@Model(searchName)`: `instanceTitle` and `recordCode` on `FlowApprovalTask`, `title` and `recordCode` on `FlowInstance`.
- **Orders replace the list's default** and end on `id`, in the direction of their first, unless they sort by it — rows tied on what was asked keep one order from page to page.

### Automation APIs

Automation flows have no endpoint to fire them by hand: data changes, Cron schedules and subflows are started by in-process consumers, and an `Api`-triggered flow is started by id through `POST /flow/instances/start`. Async-task resumes have no REST endpoint: `FlowAsyncTaskConsumer` calls `FlowRuntimeEngine` in-process.

### Event Logs

The trigger event log is the `FlowEvent` model, read through the generic model API (`/FlowEvent/searchPage`, …) with the caller's own permissions; the engine has no endpoint of its own for it.

### Approval Tasks

Base path: `/flow/approvalTasks`

| Method | Path | Description |
|---|---|---|
| `GET` | `/flow/approvalTasks/counts` | The top bar's counts for the current actor in one request (`{pendingApprovals, unreadCc, unreadNotifications}`): the `Pending` box of `/search` and the unread CC tasks, counted, and the unread inbox notifications as `GET /InboxNotification/myCountUnread` counts them (`0` without message-starter's inbox). | `GET` | `/flow/approvalTasks/instance/{instanceId}` | All tasks for one runtime instance (participants / submitter only) |

Each task `/search` lists (`FlowApprovalTaskView`) comes with its instance's context, every user, employee and department named; `/instance/{instanceId}` is the tasks an instance's own page reads, the instance already on the page, and carries the task's own fields only:

| Field | Holds |
|---|---|
| `actorName` | Its holder's name |
| `actorNames` | The names of the accounts it names, by account id: its holder and who closed it |
| `instanceTitle`, `modelName` / `rowId`, `instanceStatus`, `initiator`, `submittedTime` | Its instance's context |
| `subject`, `subjectDept`, `effectiveDate`, `recordCode`, `summary` | What a record's approval recorded of its record |
| `currentSteps` | Where a request still in approval stands now: the steps its instance waits on, with the approvers still to act, named; one query per page |
| `superseded` | Whether a later submission replaced it |
| `dueTime` | The step's due time (a step has no timeout setting of its own): when the flow sets `remindAfterHours`, that many hours after the step opened, written on the task — see [Overdue reminders](./approval#overdue-reminders) |
| `returnAllowed` | The flow's `returnEnabled` |
| `fillIn` | The step makes a field required: the approver fills it in and submits, rather than just approving |
| `batchable` | Open to its approver now — pending, the instance waiting — on a step that is not `fillIn` |

`returnAllowed`, `fillIn` and `batchable` are what its step's configuration says about acting on it, read from the revision the instance runs on. See [Batch actions](./approval#batch-actions).

The tasks are a projection of the approval history, brought up to date on every change of the instance:

| Task | One per | Status |
|---|---|---|
| Approval task | Approver and step | Closes with what its holder did: <Status>Approved</Status> <Status>Rejected</Status> <Status>Returned</Status> <Status>Transferred</Status> <Status>Delegated</Status>; a task its holder did not act on closes <Status>Withdrawn</Status> after a withdrawal, else <Status tone="cancel">Canceled</Status> (another approver ended the step, an administrator terminated the approval) |
| CC task | Recipient and step | <Status>Pending</Status> until they read it, then <Status>Read</Status>, ending when they read it |

- An approval task closes with what its holder did even when the same action went on to record more (the next step approving itself, a CC as the approval ended). Closed, it stays as it is: the others' later votes do not copy it.
- A task, open or closed, keeps its holder a participant of the instance (see [Instance APIs](#instance-apis)): the approver a termination cleared still opens the approval from their task email.
- A task also stores its instance's list fields, so the boxes filter and sort by them in the database: `instanceTitle`, `recordCode`, `modelName`, `rowId`, `initiatorId`, `submittedTime` (the instance's `createdTime`), `subjectId`, `departmentId`, `effectiveDate` — plain values, as `FlowInstance` holds them.

<Dev title="Syncing the list fields, and filling existing task rows on upgrade">

The sync copies the list fields from the instance's row when it writes a task, and an instance's never change once it starts; a view shows the task's own copy only when the instance row is gone, its instance's values otherwise.

**Upgrading**: the scanner adds the nine columns to `flow_approval_task` when the new jar boots; rows written before are filled from their instance by a SQL the deploying application ships, run after the new jar has started (a row still open is also filled the next time the sync updates it). It sets the nine columns from `flow_instance` — `title` → `instance_title`, `created_time` → `submitted_time`, the rest by the same name — joined on `tenant_id` and `instance_id`, only on rows whose `submitted_time` is still null, so a second run changes nothing; a task whose instance was purged keeps nulls. Until it has run, the boxes still list every task and show its instance's values, but a filter on those fields misses the unfilled rows and a sort on them puts them at one end. On an environment whose scanner applies nothing (an empty `scanner-scope`), the application adds the columns and their catalog rows first, as for any annotation change there.

</Dev>

Base path: `/flow/approvalRecords`

| Method | Path | Description |
|---|---|---|
| `GET` | `/flow/approvalRecords/instance/{instanceId}` | Approval history by runtime instance |

An entry (`FlowApprovalRecord`, `FlowApprovalRecordView`) records:

- its `action` (`ApprovalActionType`: `APPROVE`, `AUTO_APPROVE`, `REJECT`, `TRANSFER`, `DELEGATE`, `ADD_SIGN`, `CC`, `READ`, `RETURN`, `WITHDRAW`, `URGE`, `COMMENT`, `TERMINATE`, `RETRY`); `ADD_SIGN` and `DELEGATE` appear only in history recorded before the add-sign actions and the manual delegate action were removed;

### Delegation

Base path: `/flow/delegations`

| Method | Path | Description |
|---|---|---|
| `POST` | `/flow/delegations` | Create a delegation rule |
| `POST` | `/flow/delegations/search` | One page of the caller's own delegation rules (`FlowDelegationSearchRequest`): with `box` `Mine`, the rules routing the caller's tasks, whatever their status; with `ToMe`, the rules routing others' tasks to the caller, now or later (neither cancelled nor ended). Newest first; `filters` / `orders` may name only stored fields of `FlowDelegation`, else `400`; the filters are ANDed onto the caller and the box, never replacing them, and `orders` replace the default order |
| `GET` | `/flow/delegations/flows` | The flows a rule can be scoped to: every enabled Approval flow of the caller's tenant with an effective revision, sorted by name, each with that revision's approval steps — `[{flowId, flowName, nodes: [{nodeId, label}]}]` (`FlowDelegationFlowView`). Read past the caller's row scope, so an employee sees them all |
| `POST` | `/flow/delegations/{id}/cancel` | Cancel one of the caller's delegation rules; another user's is refused (403) |

- **Period and status**: a rule is in force over its period — from its start time (its creation without one) until its end time (its cancellation without one); the tasks arriving within it go to the delegate, tasks already waiting stay where they are. The status is not stored but worked out from the rule each time (`FlowDelegationStatus`): <Status tone="info">Scheduled</Status> (its start time ahead), <Status tone="ok">Active</Status> (within its period), <Status tone="idle">Ended</Status> (its end time passed), <Status>Cancelled</Status> (by its delegator or an administrator). Routing a task and the lists ask the same question, so a rule a list shows as Active is one that routes tasks right now; nothing switches a rule off, and the stored `active` says only whether it was cancelled.
- **Checks**: it needs the approver and the delegate, two different people, a delegate whose account can act (see [Approver Resolution](./approval#approver-resolution)), a period with both ends that ends after it starts, and, for scope `Flow` or `Node`, a flow — and step — that `GET /flow/delegations/flows` lists; otherwise it is refused (`400`), whoever creates it.
- **A rule whose delegate cannot act does not apply**: when a task arrives and the delegate's account cannot act — it was frozen since — the task stays with the approver (in a chain, with the last delegate who can act), the instance's trace says why, and nobody is told. The approval path preview follows the same rule.
- **The lists** return `FlowDelegationView`: the rule with `delegatorName`, `delegateName`, its `status` now, and `createdBy`, who set it up (the delegator, or an administrator on their behalf).

### Directory

Base path: `/flow/directory` — what the people and department pickers list: who to transfer to, CC or delegate to, whose requests to filter by, and the people and departments a flow names. It shows a name, an employee code, a department and a position, and only of people with a login account.

> [!WARNING]
>
> The application grants these endpoints in the permissions of the pages whose pickers read them — approving, managing one's delegations, the designer, the monitor — and does not list `/flow/directory/**` in `permission.authenticated-bypass-patterns`: there the endpoint gate is skipped, and a consultant's expiry with it, so anyone signed in could list everyone.

Who can be picked:

- **A person's search (`/people`) reads the directory model**, `softa.flow.org.directory-model`, with the caller's own row scope: whom a role's holders may pick is that role's scope on the directory model. It offers only people who can act, and says nothing of who cannot (`active` is null).
- **The directory model is a read-only projection of the employees.** The employee model's own scope is the wrong one — an employee's would leave them only themselves to pick, and opening the employee model to them would open every HR field with it — so an application points the directory at a read-only projection of its employees that holds only what a directory shows (for example `EmployeeDirectory`) and gives every role a scope on it, "all" by default, narrowed where a role should see fewer. Unset, the directory model is the employee model, its scope included.
- **The designer and the operations console use `/people/all`**: they run flows rather than take part in them. `/people/all` lists every account for them — people who can no longer act on request, and accounts without an employee record, a tenant's administrators — each saying whether it can act, past the caller's row scope, and only their permissions should list it.
- **Names of people and departments already picked, and the department search,** are read past the caller's row scope.
- **Finding approvers by rule never reads the directory model**: a supervisor or a department leader is found whatever the submitter may see.

| Method | Path | Description |
|---|---|---|
| `GET` | `/flow/directory/people` | People whose login account signs in (see [Approver Resolution](./approval#approver-resolution)) matching `keyword` on the directory model's search fields (code or name), all when blank, by name, as the caller's row scope on the directory model lets them read it: `DirectoryPerson` — `id` (the account id an approver, a CC recipient or a delegate is stored as), `name`, `code`, `departmentName`, `positionName`; `active` is null |
| `GET` | `/flow/directory/people/by-ids` | The people `ids` names (comma-separated, at most 200), in that order, whatever the caller's row scope: what names a picked value once the search has moved on. An account without an employee record — a tenant administrator — comes back with its name alone, as the approval views name it (nickname, else username); an id naming no account is left out. Whether they can act is not said |
| `GET` | `/flow/directory/people/all` | For the designer and the operations console: every login account matching `keyword` — people on the directory model's search fields, accounts without an employee record on the account model's — by name, each with `active`; only those that can act unless `includeInactive=true`, as when moving work off someone who left. Past the caller's row scope |
| `GET` | `/flow/directory/people/all/by-ids` | `/people/by-ids` with `active`, for the designer and the operations console |
| `GET` | `/flow/directory/departments` | Open departments matching `keyword` on the department model's search fields (code or name), by name: `DirectoryDepartment` — `id`, `name`, `code`, `parentName` (names repeat between branches) |
| `GET` | `/flow/directory/departments/by-ids` | The departments `ids` names, closed ones included, in that order; at most 200 |

**`limit`**: `/people`, `/people/all` and `/departments` default to 20, at most 200. A picker shows more by asking again for the first 40, 60 and so on as its list is scrolled, never for a next page — `/people/all` orders people and accounts together by name in memory, which a database's collation need not agree with, so a page read on its own could repeat or skip someone. Two people of one name are ordered by id, so asking again keeps them in place.

Accounts without an employee record are not searched: what everyone picks from is their colleagues. A picker used only by administrators that must offer them too — the designer's specific people — adds them from the account model with the caller's own permissions.

The directory reads through `OrganizationService` (`searchPeople`, `searchAllPeople`, `getPeople`, `searchDepartments`, `getDepartments` — empty unless the application's service implements them; `FlowOrgService` does), the tenant always applying.

</Dev>

## Monitor

<Lead>

The administrators' console: searching instances across submitters, urging, terminating, retrying and reassigning, and creating delegation rules on an approver's behalf — all by the caller's own permissions, with no role built in.

</Lead>

Base path: `/flow/monitor`.

- **No role is built in**: each endpoint is granted like any other, and what the console reads or acts on is the caller's own permissions on `FlowInstance` — their roles' grant and data scope; taking part in an instance is not enough.
- **A department scope** (`DEPT_SUBTREE`, `MANAGED_DEPARTMENTS`) narrows by `FlowInstance.departmentId`, the department of the employee the record is about, at submission — a plain department-id column the permission-starter scopes filter by the ids of the departments in range — so a role scoped to the departments it manages sees and administers their approvals; an automation run belongs to no department. Each submission records its own department: when the employee moves between two submissions, such roles of both departments read one of the instances, and so both see the record's whole approval.
- **Opening another user's instance** (detail / overlay / trace / approval history) follows the viewing rule under [Instance APIs](#instance-apis), as for any viewer who is not a participant — whoever reads one of a record's instances opens every submission of the record's approval (see [A record's approval](#a-records-approval)). <Dev title="Storage adapters and the bundle cache (OrmFlowBundleRegistry)">

Primary storage adapters in this module:

- `OrmFlowBundleRegistry`
- `OrmFlowInstanceStore`

`OrmFlowBundleRegistry` loads nothing at startup and caches per tenant:

- **Trigger matching** reads an index of the active bundles of the tenant's enabled flows, loaded in that tenant's own context on its first event (an empty result is kept too) and merged with the platform-shared bundles (`tenantId = 0`); a context without a tenant matches the shared ones only. Entries live for 60 seconds, not configurable: every write, change-log message, submission and approval preview asks the index, so it cannot be read from the database each time. Publishing, activating a revision, or disabling or enabling a flow drops the tenant's entry at once on the instance that did it; other instances pick the change up within the TTL. Change logs of models no flow watches are not turned into trigger events.
- **Definitions** are cached by `bundleId` in a bounded LRU (a published revision never changes). A bundle of another tenant reads as not found, whether cached or not; platform-shared bundles are visible to every tenant.
- **The active revision of a flow** is read from the database on every lookup — none while the flow is disabled — so starting by `flowId` follows a publish, rollback, disable or enable made on any instance.

</Dev>

### Stored enum codes

The flow models store enum codes as text: in their enum columns (`scenario`, the statuses, approval actions) and in their JSON — `FlowDesign.designJson`, `FlowBundle.designJson` and `FlowBundle.compiledJson` hold the scenario, the trigger and node types, every option inside a node's config and an approver source's `type` / `relativeTo` / `deptScope`, and an instance keeps its state as JSON.

> [!WARNING]
>
> A read throws on a code the enum no longer has (unknown enum values are deliberately not read as null), so **renaming or removing a stored code ships a migration SQL that rewrites the stored rows, in the same change**, which the deploying application runs with its release; without one, every flow still holding the old code fails to load, publish or reapply — as the flows stored as `Process` did when that scenario was split into `Approval` and `Automation`. Renaming a key inside the JSON needs the same: an unknown key reads as absent, so its value is silently lost.

## Node Descriptor Contract

<Lead>

The editor palette is built from `FlowNodeDescriptor` records exposed through `/flow/nodeDescriptors`.

</Lead>

- descriptors include label, icon, sort order, config schema, default config, and allowed scenarios
- a config field's `type` names the editor's control
- every task node's config schema has an `outputVariable` (`string`, Output variable) after its executor's own fields: the variable its result is written to
- what a setting holds decides its type, so the editor offers the right input: `template` for text interpolated as the node runs (`multiline` for a body), `expression` for AviatorScript, `stringList` for a list of texts (recipients, field names), `json` for a free JSON payload, `variableRef` for a variable's name, a picker for a record — `rolePicker` / `userPicker` / … , or `recordPicker` naming its `model` (a mail template) — storing `valueField` (`code`) instead of the id when given, and taking a typed value no record holds with `allowCustom`; a `keyValueMap`'s `valueType` says what its values are (`expression`, `template`)
- an approval step's `approverSources` offers its sources in the order an HR administrator reaches for them — specific people, the organization's (supervisor, department leader, HRBP), then the groups' (role, position, department members) — each option saying what the editor needs to tell which settings apply: `names` (the field a group of specific people names them in, `userIds`) and `findsOne` (the source finds one person at most). A setting that applies only to some steps says so in `appliesWhen`: `severalApprovers` (the approval mode, `minCount`, `percentage`) or `approversFoundByRule` (the empty-approver strategy and its roles); the engine ignores it elsewhere, by the same rules, so the editor shows it only where it applies

`FlowNodeDescriptorRegistry` lists task nodes only for executors that are actually registered as Spring beans, so conditional executors such as `QUERY_AI` and `ASYNC_TASK` only appear when their dependencies are present.

<Dev title="Where descriptors come from">

- structural descriptors come from `BuiltinNodeDescriptorProvider`; the task nodes' are made by `FlowNodeDescriptorRegistry` from the registered `TaskExecutor`s
- there is no descriptor extension point: node types are the `FlowNodeType` enum, and a new one is a change to flow-starter itself

</Dev>
